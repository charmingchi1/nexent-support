# Nexent 项目支撑流程指导书（人工执行版）

> 版本：2026-10-12 v1.0 ｜ 适用：内网环境（不可调用外部模型、不可上传内部数据）
> 用法：本文档可打印/离线携带进入内网。一线与支撑人员按章节逐步执行；所有表格写入必须走第八章「双确认」。
> 配套：《支撑工作流与自动化设计.md》（外网侧 agent 辅助设计）、《Nexent平台部署FAQ-复刻.md》（完整版）

---

## 〇、角色与总原则

| 角色 | 职责 | 限制 |
|------|------|------|
| 问题提交人（内网） | 手动填写问题单八要素、执行自查清单 | 不能导出/上传内部数据包，只做**文字摘录** |
| 支撑（你） | 定性、答复、升级、登记 | 所有表格写入前必须完成「内容确认 + 操作允许」 |
| 责任田负责人 | 深入定位、修复 | — |

**三条铁律**
1. 内网信息不出网：日志只摘关键行，截图脱敏（IP/账号/密钥打码）；
2. 不确定的答案不当确定答案说：宁可升级，不可编造；
3. 先确认后动表：没有内容确认，不写任何记录。

## 一、第一步：问题受理 —— 八要素收集模板

> 内网人员复制此模板填写后转给支撑（IM/邮件均可，纯文字即可）：

```
【Nexent 问题单】
1. 问题现象：（一句话 + 具体表现，截图请文字描述关键部分）
2. 所属局点：（华西医院/南方医院/体验环境/…，见附录A列表）
3. 环境版本：（平台 v2.x.x；Nexent 9xx 阶段；部署方式 docker compose/离线）
4. 复现步骤：（1. 2. 3.，能稳定复现标注"必现"，否则写概率）
5. 报错信息：（手动摘录日志关键行，最多10行，脱敏）
6. 影响范围：（阻断主流程 / 部分功能受影响 / 仅体验问题；影响人数）
7. 已尝试操作：（做过什么自查、改过什么配置、结果如何）
8. 期望解决时间：（业务侧 deadline，如"本周五前"）
```

**收集要点**：现象与报错缺一不可；「已尝试操作」必须问——它能省掉一半排查时间。

## 二、第二步：快速自查 —— 内网可执行清单（不依赖外网）

提交人/一线按现象对号入座，命中即按解法自查，自查通过直接闭环：

| 现象 | 自查命令 | 一句话解法 |
|------|----------|-----------|
| 登录后缺功能/刷新掉线 | `date`（对比真实时间） | 校时 + `hwclock --systohc` 写硬件时钟 |
| Supabase 初始化失败/`can't start new thread`（Docker≤23.0） | `docker version` | 所有服务加 `security_opt: [seccomp:unconfined]`，或升级 Docker≥23.0.1 |
| 容器访问外网超时 | `iptables -t nat -L POSTROUTING -n -v \| grep 172.18` | 补 MASQUERADE 规则（重启会丢，需持久化） |
| 容器间按名称互访失败 | `firewall-cmd --zone=trusted --list-all` | 把 `br-{NetworkID}` 网桥加入防火墙信任区 |
| Supabase 容器起不来（ulimits 报错） | 看容器日志关键词 nofile/线程 | kong 服务加 `ulimits: nofile: 65536/65536` |
| clickhouse 报 `cd: null directory` | `uname -m`（是否 aarch64/鲲鹏） | 换鲲鹏版镜像包（向支撑索取 tar） |
| 改了 .env/API Key 重新部署不生效 | `docker inspect <容器> \| grep -A2 Env` | `docker compose -p nexent up -d --force-recreate <服务名>` |
| 容器无限重启 | `docker inspect` 看 OOMKilled/退出码 | 资源不足：清理或扩配额，别反复 down/up |
| 知识库创建失败/存量库消失 | `df -h`（部署盘是否 >95%） | 清磁盘到 95% 以下，解除 ES 只读块；不要调高水位线 |
| 对话首 token 慢（工具测试正常） | 检查召回 topK 配置 | 调低 topK、开 rerank、控制引用长度 |
| 新建空白智能体带了别人的提示词 | 查租户库表 app_config 废弃记录 | 清空该字段应急；升级新版根治 |

自查未命中 → 进入第三步，把八要素单转支撑。

## 三、第三步：定性判定 —— 判定树 v2（五分类终态）

> v2 变更（2026-10-12）：原「不确定」不再是分类，改为「排查中」状态（限时 30 分钟回定性或升级）；
> 新增环境事件 / 模型能力限制 / 新需求 三类终态，每类绑定专属答复模板（E/F/G）。
> 详细规范与流程图见《Nexent支撑定性规范v2.md》，此处为可打印精简版。

定性流程图（ASCII 简版）：

```
                 ┌─ P0/P1 或涉安全沙箱/北向/权限? ──是──→ 【先升级再定性】
                 ↓ 否
  Q0 根因在部署环境基础设施?（资源/磁盘/防火墙/认证波动/镜像源）
                 ├─ 是 → 【环境事件】→ 模板E · 运维记录 · 不登记
                 ↓ 否
  Q1 一条命令/一处配置可消除?
                 ├─ 操作/理解偏差 → 【使用问题】→ 模板A · 不登记
                 ├─ 配置项不当   → 【配置问题】→ 模板B · 不登记
                 ↓ 否
  Q2 代码可定位且标准环境可复现?
                 ├─ 是 → 【显式bug】→ 模板C · 升级+登记（双确认）
                 ↓ 否
  Q3 根因为模型/第三方局限, 产品无法单方修复?
                 ├─ 是 → 【模型/能力限制】→ 模板F · 录已知限制清单
                 ↓ 否
  Q4 产品能力缺失?（"暂不支持"类诉求）
                 ├─ 是 → 【新需求】→ 模板G · 记需求线索池
                 ↓ 否
  【排查中】回第二步自查检索; 满30分钟 → 模板D + 升级（第四步）
```

**四条硬规则**：①结论必须给依据（哪条FAQ/哪段代码/哪次环境核查）；②记录只有"可能/疑似"的**禁止**归入终态，一律「排查中」限期定性；③答复含「暂不支持」的，无论终态为何，同批记需求线索；④登记纪律：仅显式bug 进问题跟踪表，其余类别答复闭环即可（升级消息模板中的"初判"按五分类书写）。

## 四、第四步：升级 —— 时机、对象、话术

**升级时机**（满足其一即升级）：30 分钟内无法定性；确认 bug 但无法快速规避；答案不确定；涉及模块在责任田中无对应负责人。

**升级消息模板**（发给责任田负责人）：

```
【问题升级】<责任模块> <优先级>
现象：<一句话>
局点/版本：<局点> / v2.x.x
初判：<使用/配置/bug + 依据一句>（显式bug 附修复难度：易/中/难）
已尝试：<1-3 条>
需要你：<定位协助 / 规避方案 / 排期评估>
问题单：<已登记记录链接 或 "待登记">
```

**责任田速查**（详见附录B；负责人未填的模块升级给支撑主管协调）。

## 五、第五步：登记规范 —— 什么该登记、怎么填

**登记门槛**：确认是**真实 bug**（Q1=否 且 Q2=能定位）才登记；使用/配置问题答复闭环即可，不进台账。
**入口**：确认 bug 后由支撑登记（内网人员无法访问外网表格），两条路：
- 让提交人填「Nexent 问题登记表」表单（外网可访问时）：`https://dcnvjn24oieg.feishu.cn/share/base/shrcn2bfegdmhXN2vflCq0hBDhc`
- 或支撑代填（内网摘录信息 → 支撑录入）。

**必填字段规范**（问题跟踪表 26 字段中的核心 8 项）：

| 字段 | 填写规范 |
|------|----------|
| 问题描述 | 「现象 + 触发条件」一句话，不带主观推断 |
| 问题局点 | 必填，从 18 个选项选；拿不准选「体验环境」并备注 |
| 责任模块 | 必填（判定树 Q2 的定位结果），杜绝空着导致「待分配」积压 |
| 优先级 | 阻断主流程=P0；核心功能受损=P1；一般功能/体验=P2；边缘=P3 |
| 预期修改版本 | 按期望时间倒推（830/910/915/930/1030），不确定选「其他版本」 |
| 问题修改人 | 有明确负责人就填，没有留给责任人认领 |
| 定位结论&解决方案 | 至少写初判依据；规避方案出来后补充 |
| 问题附件 | 内网摘录的日志关键行/脱敏截图 |

**随单留痕（2026-10-20 起）**：《现网问题个人跟踪》追加行结构 A=时间 B=人员 C=事件 D=结论 E=是否闭环 **F=修复难度**（取值 待评估/易/中/难，仅支撑评估，显式bug/升级项必评）。评估四问：①改动面（单点/跨模块）②外部依赖（需谁配合）③规避现状（有规避不降难度）④复现确定性（概率性上调一档）。易=单点可本迭代修；中=跨模块需联调；难=需模型/环境/第三方/前端配合或架构级。详见《Nexent支撑定性规范v2.md》§8。

## 六、第六步：表格操作「双确认」规则（强制）

任何对项目管理一张表的**写入/修改/删除**（登记新问题、改优先级、填解决方案、验收确认、转需求 link 等），必须完成：

```
确认1【内容确认】→ 把将写入的记录草稿（字段名+值逐项列出）发给问题提交人核对事实，
                    有分歧先改再提交；不确认事实的登记是二次污染。
确认2【操作允许】→ 执行人（支撑或 agent）收到明确「可以提交」的指令后才动手；
                    agent 场景 = 展示草稿 → 等待明确确认 → 本地入队（table-write.mjs，秒级）→ 周期同步批量推送飞书 → 按资源索引回执记录链接。
```

- 写入通道（2026-10-20 起）：双确认后用 `scripts/sync/table-write.mjs` **本地入队（秒级）**，随每日 08:30 同步批量推送飞书；仅紧急需即时落表时直写（--dry-run 预览后真写，仍走双确认）；
- 撤销原则：写错的内容第一时间修正并告知受影响人，不静默改；未推送的条目可直接 `table-write.mjs --cancel <id>` 撤销；
- 批量操作（补填、清理）单独列清单走双确认，不搭车执行。

## 七、第七步：闭环与沉淀

1. **答复闭环**：非 bug 问题答复后 24h 内回访一句「问题是否解决」，未解决重新走判定树；
2. **bug 闭环**：登记 → 升级沟通 → 修复版本发布 → 验收（验收确认=通过）→ 是否闭环=是；
3. **沉淀**：每周五把本周已解决问题整理成 FAQ 新条目（现象/原因/解法三段式），更新到 FAQ 文档——同类问题第二次出现时直接引用；
4. **跟进联动（难度×优先级，规范 v2 §8.4）**：P0/P1+难 → 专项跟踪每日过账、阻塞项上报；P0/P1+易/中 → 进晨报在修清单（含老化天数）；P2/P3+难 → 建议转需求池或挂起，注明难度理由。
