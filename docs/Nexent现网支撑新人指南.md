# Nexent 现网支撑新人指南

> 版本：2026-10-13 v0.1 ｜ 适用对象：首次承担 Nexent 现网支撑的同学（外网侧，使用 agent / lark-cli 辅助）
> 定位：本文档是**导航层**——只回答「你是谁、找谁、去哪查、第一天干什么」。操作细节全部指向源头文档，不在此复制，避免与源文档脱节。
> 与《Nexent支撑流程指导书.md》的区别：指导书是**可打印带入内网的人工执行版**，逐步照做；本文档帮你建立全局认知并搭好环境，日常执行以指导书 + `nexent-support` skill 为入口。

## 一、支撑职责与边界

### 你要做的

| 环节 | 做什么 |
|------|--------|
| 受理 | 收到内网转来的问题，对照八要素补齐缺项（一次性问全，不要挤牙膏） |
| 检索 | FAQ 速查 → FAQ 全文 → 代码仓定位，找现成解法或归属模块 |
| 定性 | 按判定树 v2 给出**带依据**的分类结论 |
| 答复 | 按模板产出可直接转发的话术，交提交人过目后转发 |
| 升级 | bug / 超时 / 无主模块 → 找责任田负责人或支撑主管 |
| 登记 | 仅确认的真实 bug，走双确认 → 本地入队（table-write.mjs）→ 周期同步推送；同步评估**修复难度**记入个人跟踪表 F 列 |
| 闭环沉淀 | 24h 回访；按第 5 节分级沉淀为 FAQ 条目或独立文档 |

### 你不做的

- 不深入改代码修 bug——定位到责任模块即可，修复是责任田的事；
- 不代内网执行操作——内网无外网，你只能产出**纯文字**（话术/命令/草稿），由人复制带回执行；
- 未获用户明确 send_as_user 授权，不让 agent 代发 IM；
- 业务时限（期望解决时间）由提交人给出，不替业务拍板。

### 三条铁律（红线）

1. **内网信息不出网**：日志只摘关键行（≤10 行），截图脱敏（IP/账号/密钥打码）；不要求、不生成任何「导出上传」类指引；
2. **不确定的答案不当确定答案说**：宁可升级，不可编造；记录只有「可能/疑似」时禁止归入任何终态，一律标「排查中」并限期 30 分钟定性或升级；
3. **先确认后动表**：没有「内容确认 + 操作允许」双确认，不写任何记录；先 `--dry-run` 预览再真写。

## 二、你会和谁打交道

| 角色 | 是谁 / 在哪找 | 什么时候打交道 |
|------|--------------|----------------|
| 问题提交人（内网接口人） | 转述问题的内网同事，IM 单线联系 | 补齐八要素、答复确认、24h 回访、登记前核对事实（确认1） |

| 支撑主管 | 团队内 | 8 个无负责人模块的问题协调；30 分钟无法定性 / 答案不确定时的兜底求助 |
| 支撑同事（前辈） | 团队内 | 跟单学习、第一单复核 |

**求助路径一句话**：答案不确定或超 30 分钟 → 对应责任田负责人 → 模块无负责人（或表内未映射）→ 支撑主管。永远「宁可升级，不可编造」。

> 负责人名单不在本文档复制——会过期。以 `duty-map.md` 与「5 特性负责制」表为准。

## 四、处理流程概览

七步总览（细节全部在指导书，此处只建认知）：

```
①受理补八要素 → ②检索(FAQ速查→FAQ全文→代码仓) → ③定性(判定树v2)
    → ④答复/规避(模板A~G) → ⑤升级责任田 → ⑥登记(双确认) → ⑦沉淀(见第5节)
```

### ③ 定性：判定树精简版

依序问，前一问命中即停；完整规范与边界细则见《定性规范v2》。

```
兜底：P0/P1 或涉安全沙箱/北向接口/权限 → 先升级⑤再定性
Q0 根因在部署环境基础设施？（资源/磁盘/防火墙/认证波动/镜像源）→ 环境事件
Q1 一条命令或一处配置即可消除？→ 使用问题 / 配置问题
Q2 代码可定位且标准环境可复现？→ 显式bug
Q3 模型/第三方局限、产品无法单方修复？→ 模型/能力限制
Q4 产品能力缺失（「暂不支持」类诉求）？→ 新需求
全否 → 【排查中】回②检索；满 30 分钟 → 模板D + 升级⑤
```

### 定性结论 → 去向对照

| 终态 | 答复模板 | 登记问题跟踪表 | 其他动作 |
|------|---------|----------------|----------|
| 使用问题 | A | 否 | — |
| 配置问题 | B | 否 | 话术含命令 |
| 环境事件 | E | 否 | 告知恢复与处理进展 |
| 显式 bug | C | **是（双确认）** | ⑤升级责任田 |
| 模型/能力限制 | F | 否 | 录已知限制清单 |
| 新需求 | G | 否 | 记需求线索池（月度评审） |
| 排查中超 30 分钟 | D | — | ⑤升级 |

**四条硬规则**（详见规范 v2）：①结论必须给依据（哪条 FAQ / 哪段代码 / 哪次环境核查）；②「可能/疑似」禁止归终态；③答复含「暂不支持」的，同批记需求线索；④仅显式 bug 进问题跟踪表。

### ⑥ 登记双确认（不可跳过）

```
确认1【内容确认】登记草稿（字段名+值逐项）交提交人核对事实，有分歧先改再提交
确认2【操作允许】收到明确「可以提交」指令才动手
→ --dry-run 预览 → 真写 → 把返回的记录链接回执给用户
```

必填 8 字段的填写规范见 `templates.md` 第三节；不写系统字段，用户字段没有 open_id 就留空。

### 升级时机（满足其一）

30 分钟无法定性 ／ 确认 bug 但无法快速规避 ／ 答案不确定 ／ 模块无对应负责人。

## 五、沉淀机制：把答复变成资产

闭环时问两个问题：**①这问题还会发生吗？②解法是不是一段话术/一条命令能说清？** 按下表定去向：

| 会复发 | 复杂 | 去向 |
|--------|------|------|
| 否 | 任意 | 答复闭环，不沉淀 |
| 是 | 否（一段话术/一条命令能说清） | FAQ 新条目（现象/原因/解法三段式，写入《FAQ-复刻》） |
| 是 | 是（多步骤、跨模块协调、有前置条件） | **独立处理文档 → WeLink「项目支撑」文件夹** |
| 是，但根因是模型/第三方局限 | — | 已知限制清单 |
| 诉求而非缺陷 | — | 需求线索池（规范 v2 附录B，月度评审） |

### 触发时机（三处）

- 闭环答复时：每一单都过一遍上面两个问题（主动问一句「这个案例要不要沉淀？」）；
- 24h 回访发现「未解决」：重新判级——原打算写 FAQ 的可能升格为独立文档；
- 升级责任田过程中预感「这问题会来一批」（局点批量部署、升级潮等）：不等闭环，先建文档草稿。

### 独立文档四条规范（否则文件夹会变坟场）

1. **统一模板**（放文档头部）：

   ```
   适用版本/环境：
   现象与触发条件：
   前置检查：（可复制命令）
   处理步骤：（可复制命令，假设执行人无外网）
   验证方式：
   责任人 / 最后验证日期：
   ```

2. **命名规范**：`【Nexent】<现象关键词>处理手册-YYYYMMDD`；
3. **防孤儿索引**：放入 WeLink 后，回《FAQ-复刻》加一条**跳转条目**（现象一句话 + 文档链接），让 FAQ 检索继续兜底——否则第二次遇到时想不起 WeLink 里有没有；
4. **维护规则**：每周五例行沉淀时过一遍近期文档的「最后验证日期」；版本升级后明显失效的，标注过期或更新。

### WeLink 文档的读者不是你

放 WeLink 的根本原因是**内网同事能自助查到**。所以写作对象是内网人员：命令可直接复制执行、假设对方无外网、不依赖任何 agent/工具。外网侧 FAQ 仍是支撑自己的检索库——两边分工别混。
